# 项目开发标准流程（SOP v1.0）

> **来源**：文献工作台 dsh-litkb 从 v0.1.0 到 v0.11.1 的真实开发过程——6 个工作日、40 余次提交、40 余份文档、5 个版本标签。
> **适用**：单人或 1–3 人小队 + AI 结对，1 周–2 个月的中小型产品、插件、内部工具。
> **怎么用**：新项目从 §0 走一遍；日常开发每天看 §6；交付前看 §7–§9；每周收工看 §10。
> **原则**：流程服务于交付，不是反过来。小项目按 §0.3 裁剪，但 §0.2 的五条铁律不裁。

---

## 0. 一页速览

### 0.1 主流程

```text
立项 ──▶ 契约 ──▶ 排期 ──▶ 脚手架 ──▶ 增量开发环 ──▶ 走查/评估 ──▶ 产品化 ──▶ 发布 ──▶ 复盘
0.5d     1–2d     0.5d     P0          每版跑一次       1–2d          1–2d        0.5d     0.5d
  │        │        │        │              │               │             │           │
项目卡   数据模型  闸门表   G1 装得上      每版可演示      主路径可用      G5 可交付    tag       backlog
         标准样本  WBS      冒烟/健康      CHANGELOG       指标达标        冷启动通过   Release   下一轮
```

一句话：**先把口径定死，再把「装得上」跑通，然后一小版一小版地交付可演示的东西，最后才谈产品化和发布。**

### 0.2 五条铁律

| # | 铁律 | 含义 | 违反的后果（本项目真实教训） |
|---|---|---|---|
| 1 | **口径先于代码** | 数据字段、状态、失败态没定清楚，不写生成逻辑和界面 | 边写边改 schema，返工整层 |
| 2 | **装得上先于功能** | 部署形态是最大风险，P0 只证明「装、开、卸」 | 功能做完发现装不进宿主，全部白做 |
| 3 | **一版一件事，每版可装可演示** | 每个版本都有版本号、CHANGELOG、安装包、可回滚 tag | 大混提交，出问题无法定位、无法回滚 |
| 4 | **自证不算证** | 必须给命令输出、测试结果、真实库干跑、装机截图 | 「已完成」但用户一点就报错 |
| 5 | **失败显式** | 错误有码、有文案、有重试；已知问题主动列出 | 静默失败，用户不知道卡在哪 |

### 0.3 按项目大小裁剪

| 规模 | 周期 | 保留 | 可裁剪 |
|---|---|---|---|
| **S** 小工具/脚本/一次性任务 | 1–3 天 | 项目卡一句话、一句验收、`verify`、已知问题、可回滚提交 | 长 PRD/SRS、五张验收单、质量评估、产品化四件套 |
| **M** 插件/内部工具/小产品 | 1–2 周 | §0.2 全部 + 阶段 0/1/2/3/6/7 | 30 篇级评估、复杂迁移 |
| **L** 对外产品/多人协作 | 1–2 月 | 全流程 | 无；评估样本可缩小但不可省 |

> 再小的项目也保留三件事：**一句验收、一条自检命令、一份已知问题**。

## 1. 角色与协作协议

### 1.1 分工

| 事项 | 开发（我） | 验收（你） |
|---|---|---|
| 方案、数据结构、实现、重构 | ✅ | — |
| 自测：单测、异常路径、性能、装机 | ✅ | 只在 G1 / G5 做冷启动复核 |
| 判断「场景是否真的被解决」 | 提供演示 | ✅ |
| 判断「好不好用、要不要改文案」 | 提供演示 | ✅ |
| 判断「结论可不可信」 | 提供证据链 | ✅ 抽查 |
| 需求变更 | 给影响评估与代价 | ✅ 拍板 |

**我不做**：替用户判断「值不值得做」；把未完成说成完成；拿测试数据冒充真实数据。
**你不做**：review 代码；逐条核对需求编号；测断电/大文件/畸形输入——那是开发的活。

### 1.2 对话协议

**你（产品）怎么说**：

- 说场景、现象、期望，不说实现：
  `场景：证据链点原文 → 现象：没跳转 → 期望：跳到第 5 页并高亮`
- 一次说一件事；新想法明确说「进待定」；
- 不确定的验收标准，先问「这条怎么算过」。

**我（开发）每轮必须回**：

1. **版本号**与一句话主题；
2. **改了什么**（用户视角，不是文件清单）；
3. **怎么装**（一条命令 + 是否要完全重启）；
4. **怎么验**（3 分钟能走完的路径）；
5. **已知问题**（没有就写「无」）；
6. **下一步**（一个，不铺开）。

> 这条协议的价值：任何一轮都能被独立验收、独立回滚、独立交接。

### 1.3 变更与打断

| 情况 | 处理 |
|---|---|
| 装不上 / 数据丢失 / 结论或引用错误 | **可随时打断**当前排期，优先修 |
| 新功能、新想法 | 进「待定清单」，当前版本不插队；下个版本评估 |
| 「不好用」但说不出具体 | 一起走一遍演示，记录卡住的步骤，转成具体现象 |
| 同一阶段两次验收不通过 | 停下来复查**范围是否定错了**，不硬修 |

### 1.4 交付包五件套

每次交付（至少每个阶段闸门）附：

1. **一条安装命令**（复制即用）；
2. **3 分钟演示脚本**（照着点，不用想）；
3. **验收单**（4 条勾选）；
4. **已知问题清单**（含影响范围）；
5. **数据**：耗时、成本、准确率/覆盖率等。

> 少一件，验收就会变成「你自己看着办」，最后还是要返工。

## 2. 阶段 0 · 立项（0.5 天）

### 2.1 项目卡（7 问）

写在一页里，不超过 400 字：

1. **一句话命题**：谁，在什么场景下，用它替代现在的什么做法？
2. **三个高频场景**：按真实发生频率排序，不按功能重要性。
3. **明确不做**：至少 3 条。不写「不做」的项目，边界一定会膨胀。
4. **成功指标**：可测。例：30 篇内三轴归类 ≥ 90%、单篇 ≤ 3 分钟。
5. **最大风险**：前 3 条 + 触发信号 + 对策。
6. **交付形态**：插件 / 网页 / CLI / 文档 / 脚本。
7. **验收人与验收方式**：谁点、点多久、在哪台机器上点。

### 2.2 Day 0 前置确认

- [ ] 运行环境可装（宿主版本、Node/Python 版本、权限）；
- [ ] 依赖可达（模型/API/数据库/网络）；
- [ ] 有真实样本（≥ 3 个标准样本、≥ 10 条试标数据）；
- [ ] 存储位置与备份方式确定；
- [ ] 记录宿主/运行时版本，写进 README。

> 本项目 Day 0 的四件确认：装包可行、模型可达、30 篇测试集、空库目录。缺一件都会在 P1 变成阻塞。

### 2.3 退出条件

能用一句话说清「谁在什么场景下，用它替代现在的什么做法」，且三个场景都能在 10 分钟内演示。

## 3. 阶段 1 · 方案与契约（1–2 天）

### 3.1 文档最小集

| 文档 | 回答的问题 | 本项目对应 |
|---|---|---|
| 总体方案 | 主链路是什么？分几层？ | `01_总体方案与搭建路线图.md` |
| 产品定位 | 给谁用？不做什么？ | `02_产品定位与场景.md` |
| 信息架构与数据模型 | 数据长什么样？ID 怎么生成？ | `03_信息架构与知识模型.md` |
| 技术方案 | 选型、路由、部署、风险 | `05_插件技术方案.md` |
| PRD / SRS | 功能清单与验收标准（FR/NFR） | `06_PRD.md` / `07_需求规格书.md` |
| 开发计划 | 阶段、WBS、闸门、缓冲 | `08_开发计划.md` |

**原则**：先写「数据长什么样」和「失败长什么样」，再写界面。界面可以改，数据契约改了就是全层返工。

### 3.2 契约四件套

| 契约 | 必须写清 | 本项目的例子 |
|---|---|---|
| **数据模型** | 实体、ID 规则、必填、版本、兼容策略 | `chain = { claim, nodes[], relation }`，节点必须带 q-id |
| **状态机** | 每个实体任何时刻的唯一状态 + 失败态原因 | 收文 → 已识别 → 已归类 → 已解析 → 已精读；失败带原因 |
| **接口** | 请求/响应/错误码/幂等 | `POST /restore?confirm=restore`；`409 restore_busy` |
| **溯源** | 每个结论能回到哪 | q-id + 页码 + bbox；没有 q-id 不许进稿 |

**非功能也要有阈值**，否则「快」「便宜」「稳」无法验收：

- 单次操作耗时（本项目：单篇处理 ≤ 3 分钟、列表 ≤ 1 秒、图谱 ≤ 2 秒）；
- 单篇/单次成本；规模上限（多少篇、多大文件、多少并发）；
- 离线可用性（哪些功能不依赖网络）；
- 失败恢复时间（重启后能否续跑、备份多久能恢复）。

### 3.3 标准样本（闸门的前置）

- **3 个标准样本**：人工核对一次，作为回归基线，任何改动先跑这三篇；
- **10 条试标**：把字段口径跑一遍，确认「没有歧义」；
- **没有样本，不写生成逻辑**（prompt、规则、分类器）；
- 样本要覆盖：典型、边界、失败（扫描件/无 DOI/超长标题）。

> 本项目把「3 篇标准卡 + 30 篇测试集」写进了 Day 0 前置和 G2/G3 验收，这是后面敢改 prompt 的底气。

### 3.4 闸门 G0

- [ ] 字段口径无歧义（两个人按文档标注，结果一致）；
- [ ] 三个标准样本人工核对通过；
- [ ] 失败态都有名字，且能落到界面文案；
- [ ] 数据可导出、可备份、可重建索引。

## 4. 阶段 2 · 排期与闸门（0.5 天）

### 4.1 阶段划分四原则

1. **先证明装得上**：插件/部署类项目，P0 只做「装、开、卸」；
2. **先数据后界面**：解析/归类不通，界面再漂亮也是空壳；
3. **先证据后展示**：没有溯源的图、结论、评分都是装饰；
4. **每阶段可演示**：每个闸门都能当场点一遍，不演示不进入下一阶段。

### 4.2 阶段表

| 阶段 | 目标（一句话） | 产出 | 闸门 | 建议工期 |
|---|---|---|---|---|
| P0 脚手架 | 装得上、开得开、卸得掉 | 可安装包、健康检查、冒烟 | G1 | 1–2 天 |
| P1 主数据 | 数据进得来、看得见 | 导入、列表、基础 CRUD | G2 | 2–4 天 |
| P2 核心价值 | 用户真正要的那件事跑通 | 核心链路 + 证据/校验 | G3 | 3–5 天 |
| P3 增强 | 批量、对比、导出、自动化 | 效率功能 | G4 | 3–5 天 |
| P4 产品化 | 别人能独立用起来 | 上手、备份、诊断、安装器 | G5 | 1–2 天 |
| P5 收口 | 可发布、可维护 | 文档、评估、发布包 | G6 | 0.5–1 天 |

> 每个阶段最多 5 个任务、每个任务 0.5–1 天。超过就是没拆细。

### 4.3 WBS 粒度

每个任务一行，必须有：

| 字段 | 要求 |
|---|---|
| ID | `P2-3`，可被验收单和提交信息引用 |
| 产出物 | 一个能打开/能调用/能看的东西，不是「写代码」 |
| 依赖 | 前置任务 ID；关键路径标出来 |
| 验收 | 一句可点击/可命令验证的话 |
| 状态 | 待做 / 进行 / 已交付 vX.Y.Z / 延后（原因） |

**卡点前置**：关键路径上最大的不确定性（如中文 PDF 解析质量），必须在进入下一阶段前给出「继续/换方案」的决定，不能拖。

### 4.4 缓冲与冻结

- 预留 **10–15%** 缓冲，只用于已识别风险，不用于加需求；
- 需求基线冻结；新想法进「待定清单」，标来源与价值；
- 只有三类情况允许改范围：**装不上、数据丢失、引用/结论错误**。

### 4.5 闸门验收单格式

每张 4 条，每条「你做什么 / 通过标准」，15 分钟内能走完：

```text
G3 · 读得懂
1. 随便点开一篇 → 七段都能读，没有「待补充」空段
2. 点一条证据 → 跳到对应页并高亮
3. 改状态为「精读」→ 重开仍是「精读」
4. 删掉 PDF 再打开卡片 → 明确提示断链，不崩溃
```

结论三态：✅ 通过 / 🟡 有条件通过（遗留项不影响本阶段价值）/ ❌ 不通过（主路径不可用）。

## 5. 阶段 3 · 脚手架（P0）

### 5.1 垂直切片清单

第一个可交付版本必须包含：

- [ ] **装**：一条命令安装，失败能还原；
- [ ] **开**：入口出现，能打开、能关闭、不白屏；
- [ ] **卸**：卸载后入口消失，无残留；
- [ ] **健康检查**：`/health` 返回版本与关键依赖状态；
- [ ] **诊断**：`/diag` 返回库路径、运行时、计数（出问题能自救）；
- [ ] **日志/错误**：失败有码、有文案、有落点；
- [ ] **冒烟测试**：装 → 开 → 卸 自动化或半自动化；
- [ ] **数据目录**：默认路径 + 环境变量覆盖 + 首次自动初始化。

### 5.2 可观测三件套

1. **版本可见**：页脚、关于页、`/health` 三处一致；
2. **数据可见**：多少条、多大体积、最近备份；
3. **失败可见**：任务失败有原因、可重试、可取消。

### 5.3 闸门 G1

- [ ] 在**干净环境**（或新 profile）按文档装一次成功；
- [ ] 5 分钟内出现入口，能开能关；
- [ ] 卸载干净；
- [ ] 与既有插件/工具不冲突；
- [ ] 冒烟脚本通过。

> 本项目 P0 只干这一件事，因为「插件装不进去」是当时最大的风险。先排除它，后面才敢做功能。

## 6. 阶段 4 · 增量开发环（核心，每个版本跑一遍）

### 6.0 七步环

```text
① 取任务 ──▶ ② 定改动面 ──▶ ③ 实现 ──▶ ④ 测试 ──▶ ⑤ verify ──▶ ⑥ 记账 ──▶ ⑦ 装机验证
    ▲                                                                              │
    └────────────────────── 用户验收 / 现象反馈 ◀──────────────────────────────────┘
```

| 步骤 | 产出 | 退出条件 |
|---|---|---|
| ① 取任务 | 一句验收 | 「用户做什么 → 看到什么；失败看到什么」写得出 |
| ② 定改动面 | 影响清单 | 五层都过一遍，知道还有谁在读这份数据 |
| ③ 实现 | 可构建的代码 | 不改生成物，不跨职责，命名不冲突 |
| ④ 测试 | 新增/更新的测试 | 至少覆盖成功 + 一个失败路径 |
| ⑤ 自检 | `verify` 输出 | 全绿；没跑不算完成 |
| ⑥ 记账 | 版本 + CHANGELOG + 文档 + 提交 | 三处版本号一致，提交可回滚 |
| ⑦ 装机验证 | 健康检查 + 截图/演示 | 真实宿主里点通主路径 |

### 6.1 取任务：写成一句验收

模板：

```text
场景：<在哪个页面/命令，做什么>
期望：<看到什么，可量化>
失败：<失败时看到什么，能否重试>
```

任务来源，优先级从高到低：

1. 用户报的现象（有具体复现步骤）；
2. 功能清单里的 🟡/⏸ 项；
3. 业务走查表里的「待定」项；
4. 质量评估里低于阈值的项；
5. 自己想到的优化（**最后**，且要能说出场景）。

不接的任务：「优化一下」「美化一下」「完善一下」——先问出场景，再决定做不做。

### 6.2 定改动面：五层清单

| 层 | 要问的问题 |
|---|---|
| 数据 | 加字段吗？旧数据兼容吗？要不要迁移/回填？ |
| 接口 | 新路由？错误码？幂等？权限？ |
| 逻辑 | 状态机变了吗？失败分支齐吗？并发/重复请求呢？ |
| 界面 | 空态/加载/错误/长文本/窄屏？入口唯一吗？ |
| 工具/文档 | Agent 工具、导出、API 文档、功能清单、CHANGELOG |

**强制两问**（本项目踩过的坑）：

1. **同一个动作有几个入口？** 改了一个，另一个改了吗？
   > v0.9.1：卡片页的选区建链改了，解析页仍是旧逻辑，用户看到的行为不一致。
2. **这份数据还有谁在读？** 列表、详情、导出、检索、图谱、统计、备份、Agent 工具。
   > 加字段只改一处，导出/备份静默丢数据，是最难发现的一类 bug。

**规模判断**：改动超过 5 个文件，或跨 3 层以上，先写 1 页方案（目标/方案/影响/回滚），再动手。

### 6.3 实现约定

| 约定 | 原因 |
|---|---|
| 源码分片，**生成物不手改** | `lib/` 由 `src/` 拼接生成；手改下次构建就丢 |
| 新路由四件套：注册 + 冒烟列表 + API 文档 + 前端调用 | 少一件就会出现「404 但代码里有」 |
| 命名唯一：CSS 类/组件名前缀化，不复用旧名 | v0.8.2 类名撞车，右侧面板塌成 14px |
| 失败显式：错误码 + 可读文案 + 重试入口 | 「没反应」是最贵的 bug |
| 兼容旧数据：读取时兼容，写新不写死 | 升级不能要求用户重建库 |
| 一次只动一件事 | 出问题能二分定位，能单独回滚 |
| 不引入不必要的依赖 | 依赖是长期维护成本；本项目客户端零 bundler |

### 6.4 测试四层

| 层 | 测什么 | 做法 | 本项目的例子 |
|---|---|---|---|
| **单元** | 纯函数、规则、边界 | 临时目录 + 直接 import；断言输入输出 | 链去重、段落合并、页码校验 |
| **路由** | 请求/响应/错误码/幂等 | 临时库，直接调 handler | 备份校验、恢复 428/413/422 |
| **界面** | 结构/文案/类名/状态 | DOM 断言（假 React / 字符串断言），不依赖浏览器 | 抽屉必须有标题、图谱必须有高度 |
| **真实库干跑** | 端到端 + 规模 + 真实脏数据 | 复制真实库跑脚本，逐条审计 | 47 条边逐条核对 47/47 合法 |
| **回归样本** | 3 个标准样本 | 每次改规则/prompt 都跑 | 三篇标准卡对比 |

**原则**：

- 每修一个 bug，补一条**能复现该 bug 的断言**，防止复发；
- 测试通过 ≠ 功能可用：还要在真实宿主里点一遍（见 6.7）；
- 测试数据不能冒充真实数据；真实库干跑要写清样本量。

### 6.5 自检命令

项目必须有一条**总门禁**命令，把「能提交」定义清楚：

```bash
npm run verify   # check + lint + format:check + test
npm run coverage # 覆盖率门槛：lines 70 / functions 65
```

规则：

- **没跑 `verify` 不算完成**，口头「应该没问题」不算；
- CI 跑同一套命令，本地过 CI 才可能过；
- 覆盖率只设下限，不为凑数写无意义测试；
- 前端/交互类项目额外加：`format:check` + 结构断言 + 真实宿主截图。

### 6.6 记账（每版必做）

| 项 | 规则 |
|---|---|
| **版本号** | 修 bug/文案/样式 → patch；新能力/新接口/新字段/行为变化 → minor；三处同步：`package.json`、`package-lock.json`、`dsh.plugin.json` |
| **CHANGELOG** | 一条，写「用户看到的变化」，不写实现细节；附路由数/测试数变化；日期 |
| **文档** | 新功能 → 方案/交付单；行为变化 → 功能清单；版本 → README/交付说明/文档索引 |
| **提交** | 一个提交一件事；`feat:` / `fix:` / `docs:` / `chore:` / `release:`；标题末尾带版本号 |
| **tag** | 每个交付版本打 tag，保证可回滚；发布版本打附注 tag |

> 本项目的 v0.2.x 一天发了 14 个版本（v0.2.1–v0.2.14），每个都能装、能回滚；小步提交是「敢改」的前提。

### 6.9 前端专项检查（真实 bug 转化）

每轮 UI 改动，过一遍这 8 条：

| # | 检查 | 真实来源 |
|---|---|---|
| 1 | **高度链**：`height:100%` 的每一级父容器都有确定高度吗？ | v0.11.1 图谱空白：`.litkb-kb` 解析为 0 高 |
| 2 | **定位祖先**：`absolute/fixed` 相对谁？祖先里有没有 `overflow`/`transform`？ | v0.6.1 抽屉相对滚动容器定位，标题被卷走 |
| 3 | **类名冲突**：新组件有没有复用旧类名？ | v0.8.2 复选框复用面板类，被压成 14px |
| 4 | **溢出裁切**：祖先 `overflow:hidden` 会不会切掉菜单/浮层？ | v0.11.1 下拉被工作台页裁切 |
| 5 | **对比度**：深底深字、浅底浅字？主/次/禁用三态都看 | v0.8.1 选区工具条深底深字 |
| 6 | **状态齐全**：空、加载、错误、超长文本、窄屏、禁用 | v0.2.7 字号/溢出专项 |
| 7 | **多入口一致**：同一动作在几个页面出现，是否都改了 | v0.9.1 解析页与卡片页行为不一致 |
| 8 | **每个修复补断言**：CSS/结构断言防复发 | v0.8.2、v0.11.1 都补了回归断言 |

### 6.10 数据改动专项

只要动数据（加字段、迁移、备份、导入导出）：

- [ ] **先备份**：改之前能一键导出/快照；
- [ ] **兼容读**：旧记录缺字段时有默认值，不崩；
- [ ] **破坏性操作二次确认**：删除、覆盖、恢复要输入确认词；
- [ ] **失败可回滚**：记录已替换清单，失败按清单回滚；
- [ ] **排除敏感数据**：令牌、缓存不进备份；
- [ ] **大小/路径校验**：防 zip bomb、防路径穿越；
- [ ] **并发保护**：恢复中再次请求返回 409；
- [ ] **导出覆盖新字段**：JSON/CSV/备份三处都检查。

> 本项目的恢复顺序：校验 zip → 校验 manifest → 逐条校验路径 → staging 解压 → 当前库快照 → 逐目录替换 → 失败回滚 → 清理。这个顺序可以复用到任何「整库导入」。

### 6.11 patch 还是 minor

| 情况 | 版本 | 例子 |
|---|---|---|
| 修 bug、文案、样式、无接口变化 | patch | v0.8.1 工具条、v0.11.1 图谱高度 |
| 新接口/新页面/新字段/行为变化 | minor | v0.11.0 备份恢复、v0.9.0 证据优先建链 |
| 破坏性变更/对外重编号 | major 或 min 的 x.0.0 | v0.1.0 对外重编号 |

> 一天可以发多个 patch，但**每个都要能装、能回滚、有 CHANGELOG**。宁可版本多，不可版本乱。

### 6.12 每日节奏

| 时点 | 做什么 | 产出 |
|---|---|---|
| 开工 10 分钟 | 读工作总览 + 昨日 CHANGELOG + 待定清单 | 今天 1–3 个版本目标 |
| 开发中 | 每版走 §6 七步环 | 可演示的版本 |
| 收工 10 分钟 | 更新功能清单/总览、提交、打包、记未完成与风险 | 第二天能接着干 |
| 每周五 | 业务走查 + 质量评估 + 更新总览 | 下周 backlog |

### 6.13 安全与隐私（交付前必查）

- [ ] **本地优先、最小外发**：只把必要文本发给模型/OCR，不上传整库、不传附件；
- [ ] **密钥四不入**：不入库、不入备份、不入日志、不进提交（令牌放本机设置）；
- [ ] **真实数据不进仓库**：PDF、卡片、截图、路径中的个人信息提交前清理；
- [ ] **删除/覆盖/恢复二次确认**，且都有回滚路径；
- [ ] **安装与依赖可审计**：不用来路不明的安装脚本，依赖锁版本；
- [ ] **无遥测**：若收集任何数据，必须在「关于」里写明并默认关闭。

## 7. 阶段 5 · 走查与评估

### 7.1 业务细节走查（不拓功能）

**目标**：把现有每个业务的入口、状态、文案、数据一致性逐块过一遍，不加新功能。

**顺序**：主模块 → 次级视图 → 设置/管理 → 导入。

**每块固定 6 项**：

1. 入口是否唯一？有没有重复/无效按钮？
2. 空态、加载、错误、长文本、窄屏是否都有？
3. 按钮尺寸/文案/危险操作确认是否统一？
4. 数据一致性：列表与详情、统计与筛选、导出与当前筛选是否对得上？
5. 已知欠账是否仍成立？要不要本轮修？
6. 术语是否统一？（「论文/文献」「证据链/论证链」「研究/主题」）

**做法**：先列问题 → 当场修低风险项 → 需要决策的留到本轮末尾，不打断节奏。

**产出**：一张走查表（检查项 / 现状 / 处理），未修项进待定清单。

> 本项目的走查表直接变成了 v0.7.x 的需求来源：入口收进「更多 ▾」、导出收进菜单、DOI 判重、任务取消/续跑，都是走查出来的，不是拍脑袋加的。

### 7.2 质量评估（可量化）

| 项 | 规则 |
|---|---|
| 样本 | 30 篇：10 篇核心 + 20 篇随机/边缘；覆盖期刊/会议/学位论文 |
| 自动指标 | 覆盖率、证据可定位率、重复组、引用解析率 |
| 人工评分 | 切题度/支撑度/groundedness，1–5 分，≥3 计入 |
| 通过线 | 可定位 ≥ 98%、precision 均值 ≥ 3.5、覆盖 ≥ 80%、groundedness ≥ 3.5、引用 100% |
| 修正原则 | **按频率修，不按单条特例改规则** |

**必须诚实区分**：自动脚本能算的（可定位率）≠ 人判断的（切题、支撑）。报告里分开写，不混成一个「准确率」。

### 7.3 边界清单

交付说明里必须有两张表：

- **明确没做**（产品边界）：概念图谱 UI 隐藏、LLM 重排未接、云同步不做；
- **已知限制**（有影响范围）：双栏阅读顺序仍按块顺序、<900px 未适配、真实 30 篇评估待做。

> 「没做」和「做坏了」是两回事，写在不同的表里。

### 7.4 闸门 G3 / G4

- [ ] 主路径 0 阻断（点得通、不报错、不白屏）；
- [ ] 关键指标达标，或低于阈值但有明确原因与下一步；
- [ ] 已知问题都有影响范围说明；
- [ ] 用户能在不看文档的情况下走完主路径（G5 预演）。

## 8. 阶段 6 · 产品化（1–2 天）

功能闭环 ≠ 可交付。产品化只做四件事：

| 事项 | 用户问题 | 最小做法 |
|---|---|---|
| **上手** | 我第一次打开先做什么？ | 空库欢迎页 + 3–5 步进度（按真实数据打勾） |
| **数据安全** | 换机/升级/误删怎么办？ | 一键备份 + 恢复 + 覆盖前自动快照 |
| **可诊断** | 出问题怎么排查？ | 关于页（版本/环境/体积）+ 一键复制诊断信息 |
| **可安装** | 怎么装到另一台机器？ | 安装器（tgz/link、失败还原）+ 卸载 + 回滚说明 |

### 8.1 备份与恢复（可直接复用）

**备份范围**：业务数据全量（文档、索引、附件、配置中的非敏感项）。

**排除**：令牌、缓存、临时文件、依赖目录。

**恢复安全顺序**（不可颠倒）：

```text
校验包（格式/大小/manifest）
  → 逐条校验路径（拒绝绝对路径、..、空段）
  → 解压到 staging
  → 当前库打包快照
  → 逐目录替换，记录已替换清单
  → 任一步失败：按清单回滚
  → 清理临时目录
```

配套限制：包 ≤ 512MB、解压 ≤ 2GB、恢复中再次请求 409、错误码明确（428/413/422）。

### 8.2 冷启动验收（G5）

在**空库**环境，不看文档，5 分钟内走完：导入 → 生成 → 建链/核心动作 → 备份。

- [ ] 空库有欢迎页，不是空白；
- [ ] 每一步都有下一步提示；
- [ ] 完成后引导自动消失，不打扰；
- [ ] 卸载重装数据完好；
- [ ] 备份能恢复，恢复前有快照。

- [ ] `npm run verify` 全绿（check + lint + format + test）；
- [ ] `npm run coverage` 达标；
- [ ] 版本号三处一致（package / lock / plugin manifest）；

- [ ] 已知问题清单已更新；
- [ ] 备份/恢复在干净库上验过一次。

### 9.2 打包与 Git

```bash
# 1. 版本
npm version 0.11.1 --no-git-tag-version   # 同步改 dsh.plugin.json

# 2. 构建 + 质量门
npm run build && npm run verify && npm run coverage

# 3. 打包
npm pack                                  # → dsh-litkb-0.11.1.tgz

# 4. 提交与标签
git add -A
git commit -m "release: v0.11.1"
git tag -a v0.11.1 -m "dsh-litkb v0.11.1"
git push origin main && git push origin v0.11.1

# 5. Release（附 tgz）
gh release create v0.11.1 dsh-litkb-0.11.1.tgz \
  --title "dsh-litkb v0.11.1" --notes-file CHANGELOG.md
```

### 9.3 发布后复核（15 分钟）

1. 用发布包在干净 profile 安装一次；
2. 完全重启 + 强刷；
3. `/health` 版本正确；
4. 主路径点 3 条；
5. 记录安装耗时与任何异常。

### 9.4 回滚预案

| 层 | 回滚方式 |
|---|---|
| 代码 | `git checkout <上一版 tag>` 或安装上一版 tgz |
| 数据 | 从备份恢复；恢复前会自动再快照 |
| 配置 | manifest 备份文件（安装器自动生成） |

> 发布前必须确认：**上一版 tag 能装、上一版备份能恢复**。只备份不演练，等于没备份。

## 10. 阶段 8 · 复盘与下一轮（0.5 天）

### 10.1 一页总览（每版更新）

把散落在交付单里的进度收成一张表：

1. 一页速览：产品、版本、周期、规模（路由/工具/测试/代码量）、状态；
2. 时间线：阶段 → 日期 → 版本 → 关键能力；
3. 现在能做什么（按用户动作，不按模块）；
4. 模块完成度：✅ / 🟡 / ⏸，每条有依据；
5. 工程量与真实库快照；
6. 明确没做与已知边界；
7. 下一步优先级（P0–P3 + 理由）。

### 10.2 backlog 排序

| 优先级 | 判断标准 | 例子 |
|---|---|---|
| P0 | 交付闸门/数据安全/用户主路径阻断 | 真实 30 篇评估、Agent 端到端验收 |
| P1 | 高频场景的体验缺口、有数据支撑 | 检索缓存、研究间对比 |
| P2 | 长期稳定性（任务续跑、自动备份） | 文件夹监控、快照清理 |
| P3 | 工程优化（类型、模块化、性能） | ESM、类型检查 |

> 排序依据是「用户现在卡在哪」，不是「哪块代码最丑」。

### 10.3 复盘三问

1. **哪次返工本来可以避免？**（是不是口径没定、样本没跑、入口没查）
2. **哪份文档与实现漂移了？**（索引、功能清单、README 版本）
3. **哪个闸门没拦住问题？**（测试过了但装机失败？验收单太虚？）

答案写进下一轮的「流程修正」，不是写进检讨。

### 10.4 什么时候不发版

- 改动没跑 `verify`；
- 装不上或装完主路径不通；
- 数据迁移没有回滚方案；
- CHANGELOG 写不出「用户看到的变化」；
- 只是「想发个版」。

## 11. 文档体系

### 11.1 分层与编号

| 编号 | 类型 | 是否随版本更新 |
|---|---|---|
| `01`–`09` | 方案与契约（总体、定位、数据、技术、PRD、SRS、计划、验收协议） | 长期有效，改版加变更说明 |
| `10`–`18` | 阶段交付单 | **历史**，保留原文 |
| `19`–`26` | 功能清单与专项方案 | 功能清单随版本更新；专项方案冻结 |
| `27`–`31` | 交付说明、安装发布、数据模型、排障 | 随版本更新 |
| `32`–`42` | 工作总览、新方案、质量评估、产品化 | 总览随版本；方案冻结 |
| `43+` | 流程、模板、索引 | 长期有效 |

### 11.2 单一事实源

同一件事只允许一个地方说了算：

| 想知道 | 只看 |
|---|---|
| 现在有什么功能、什么状态 | `19_功能清单.md` |
| 怎么装、怎么验、边界是什么 | `27_正式交付说明.md` |
| 这个版本做了什么 | `CHANGELOG.md` + 对应交付单 |
| 整体进度与下一步 | `32_已完成工作总览.md` |
| 文档该读哪份 | `docs/README.md` |

其他文档引用它们，不复制结论。复制就会漂移。

### 11.3 更新矩阵

| 改了什么 | 必须更新 |
|---|---|
| 新增功能/接口 | 方案或交付单 + 功能清单 + CHANGELOG + API 文档 + 文档索引 |
| 行为/文案/交互变化 | 功能清单 + CHANGELOG（用户视角） |
| 数据模型/迁移 | 数据模型文档 + 备份范围 + 功能清单 |

### 11.4 历史文档处理

- **不追改**历史交付单，在开头标「历史记录，以 19/27/32 为准」；
- 索引里分「当前有效 / 历史记录」两栏；
- 被替代的方案标注「已被 XX 替代」；

### 11.5 文档即上下文（AI 结对的关键）

新会话/新接手人，按顺序读三样就能接着干：

1. `32_已完成工作总览.md`（现在到哪了）；
2. `CHANGELOG.md` 最近 3 条（最近改了什么、为什么）；
3. 待定清单（接下来做什么、什么不做）。

> 本项目 6 天里换了多次会话，靠的就是这条：**文档是记忆，聊天记录不是**。

## 12. 质量门与命令（本项目落地）

| 命令 | 作用 | 阈值/说明 |
|---|---|---|
| `npm run build` | 从 `src/` 拼接生成 `lib/` | 生成物不手改 |
| `npm run check` | 所有服务端模块语法检查 | 必须过 |
| `npm run lint` | ESLint 9 | 0 error 0 warning |
| `npm run format:check` | Prettier 3 | 必须过 |
| `npm test` | 136 项 / 34 个测试文件 | 全过，exit 0 |
| `npm run coverage` | c8 覆盖率 | lines ≥ 70 / functions ≥ 65 |
| `npm run verify` | check + lint + format + test | **交付总门禁** |
| `npm run eval` | 质量评估导出 report/scores/summary | 人工填分 |
| `npm run plugin:install` | 安装到 profile（tgz 或 link） | 失败自动还原 |
| `npm pack` | 产出 tgz | 发布用 |

CI（GitHub Actions）：`check → format → lint → test → coverage`，与本地同一条链。

> **换项目时**：命令可以换，结构不能丢——每个项目都要有一条「一条命令证明能提交」的总门禁，和一条「一条命令装上去」的安装命令。

## 13. 反模式清单

| # | 反模式 | 真实后果 | 正确做法 |
|---|---|---|---|
| 1 | 边写代码边改数据模型 | schema 反复，全层返工 | 阶段 1 定契约，改契约要写影响评估 |
| 2 | 先做界面后做数据 | 漂亮空壳，演示不了 | 先数据后界面 |
| 3 | 功能做完才发现装不上 | 全白做 | P0 只做装/开/卸 |
| 4 | 改了 A 页面忘了 B 页面 | 同一动作两种行为（v0.9.1） | 改动面前先列「同一交互的所有入口」 |
| 5 | 复用旧 CSS 类名 | 页面塌陷（v0.8.2） | 组件类名前缀化 + 回归断言 |
| 6 | 只跑单测就宣布完成 | 装机 404、白屏 | `verify` + 真实宿主点主路径 |
| 7 | 只刷新页面就以为更新了 | 新路由 404、旧前端 | 完全重启 + 强刷 + `/health` 对版本 |
| 8 | 版本号只改一处 | 关于页/健康检查版本不一致 | 三处同步 + 发布清单 |
| 9 | 手改生成物 | 下次构建丢失 | 改 `src/`，重新 build |
| 10 | 文档写「已完成」但没验 | 信任崩塌 | 每条结论附命令输出/截图/数据 |
| 11 | 新想法直接插队 | 版本范围膨胀，交付延期 | 待定清单，下版评估 |
| 12 | 备份了但没演过恢复 | 真出事恢复不了 | 发布前在干净库演练一次 |
| 13 | 用测试数据冒充真实数据 | 指标虚高，上线翻车 | 真实库干跑，样本量写清楚 |
| 14 | 大混提交 | 出问题无法二分、无法回滚 | 一提交一件事，一版一个 tag |
