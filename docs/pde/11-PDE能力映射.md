## 一、PDE 是什么（本案口径）

> PDE（Product Design Engineer）：能同时承担**产品定义、体验设计、工程实现**，并对最终交付负责的角色。

不是「会写代码的设计师」，也不是「会画图的产品经理」，而是**对「问题 → 方案 → 上线 → 结果」整条链路负责**的人。
本案按这个口径组织证据：每一段都对应「做了什么判断、落到什么设计、写成什么代码、怎么验证」。

## 三、三项可迁移的方法

### 3.1 七步交付环

```text
一句验收 → 五层影响 → 实现 → 四层测试 → verify → 记账 → 装机验证
```

价值：把「做完」定义成可验证的状态，而不是「我觉得好了」。
迁移场景：任何有真实用户、需要上线的产品。

### 3.2 证据优先

- 任何结论必须能回到原始材料（原文/数据/日志）；
- 自动产出只做草稿，人确认后才生效；
- 度量打在「模型/数据做了什么」上，不打在「系统最终存了什么」上。

迁移场景：AI 产品、研究工具、内容审核、数据分析。

### 3.3 结构断言

- 每个修过的 bug 补一条结构断言（不是「再看一眼」）；
- 双入口、DOM 高度链、定位祖先、类名冲突，都是可断言的；
- 断言进 CI，返工才不会再犯。

迁移场景：任何前端/可视化产品。

## 四、这个案例证明了什么

| 证明了 | 证据 |
|---|---|
| 一个人可以在 6 天内交付一个可安装的 AI 产品 | 40+ 版本、7 个 tag、安装器、冷启动验收 |
| 「可信」可以做成产品约束 | q-id 强制、草稿审核、引用校验、无模型降级 |
| 小步版本能显著降低返工成本 | 40+ 版本、每个可回滚；5 个 bug 快速定位 |
| 设计系统能减少 UI 返工 | 439 hex → 令牌；8 条结构断言 |
| 诚实边界能建立信任 | 30 篇/Agent E2E/概念图都明写「未做」 |

## 五、这个案例没证明什么

| 没证明 | 为什么重要 | 怎么补 |
|---|---|---|
| 用户愿意改变习惯 | 决定产品是否有市场 | 3–5 位研究者试用 + 访谈 |
| 30 篇规模可用 | 决定能否作为日常工具 | 30 篇真实库 + 人工评分 |
| 链的语义质量 | 决定「可信」是否成立 | precision/groundedness 评分 |
| 长期维护成本 | 决定能否持续 | 3 个月使用 + 缺陷率 |
| 团队协作下的表现 | 决定能否产品化 | 多人协作/权限另行验证 |

## 八、结论

PDE 的稀缺不是「会三样」，是**对交付结果负责**：
能在问题不清时定口径、在资源有限时做取舍、在功能诱惑前守边界、在上线之后认欠账。
本案的证据支持「端到端独立交付」；不支持「用户价值已验证」。这两句话要一起说，才是完整的 PDE 自评。
