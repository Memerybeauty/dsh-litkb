# 文献工作台 dsh-litkb · PDE 交付案例

> 一个本地优先的文献研究 Agent：从「读过的论文会忘」到「每条结论都能回到原文」。
> 本包按 PDE（Product Design Engineer）的端到端交付口径写成：问题 → 场景 → 方案 → POC → 产品设计 → 技术方案 → 实现 → 测试 → 上线 → 复盘。

| 项 | 内容 |
|---|---|
| 项目 | 文献工作台（`dsh-litkb`），装进 DeepSeek Harness 的本地文献知识库 |
| 交付形态 | DSH Web 插件（服务端 + 客户端双端），数据落在本机文件夹 |
| 周期 | 2026-11-04 → 2026-11-10，6 个工作日，v0.1.0 → v0.13.0 |
| 写作基线 | **v0.13.0**（已提交、已打 tag） |
| 规模 | 86 条 HTTP 路由 · 12 个 `lit_*` Agent 工具 · 35 个测试文件 · 源码约 12.5k 行 |
| 真实库 | 4 篇论文 / 4 张卡 / 47 条证据边 / 58 个概念 |
| 质量 | 136 项测试（v0.11.1 记录）· CI 全绿 · 覆盖率 79.3% 行 / 57.8% 分支 / 78.4% 函数 |
| 状态 | 主链路闭环 + 产品化收口；30 篇人工评估、Agent 真实对话验收仍待做 |

## 一、一页结论

1. **问题不是「读得慢」，是「读完留不下可复用的证据」。** 收藏夹里 35 篇 PDF，写作时仍然靠 Ctrl+F 和记忆；真正缺的是「这句话出自哪篇、哪页、能不能直接进稿」。
2. **产品把「证据」做成第一等公民。** 每条结论绑定 q-id + 页码 + bbox；没有库内证据的结论不许进稿。这是整个产品的信任底座，也是它区别于「PDF 聊天框」的地方。
3. **设计上做了四个反直觉取舍**：自动建链只出草稿、必须人工审核；概念图谱先隐藏、证据链图先上；界面从多页收敛成单页大卡片；数据本地优先、不做云同步。每一个取舍都能说出「放弃了什么」。
4. **工程上用「双端插件 + 无 bundler 拼接」换部署确定性。** `src/` 分片按文件名拼成 `lib/`，没有打包器，没有运行时构建；86 条路由、12 个工具、12.5k 行源码，装机只需要一条命令。
5. **质量不是「测试过了」，是「真实库审过」。** 47 条证据边逐条审计 47/47 可追溯；首次 eval 的可定位率只有 54%，定位到脚本口径 bug 后重跑 100%——这个 54% 比 100% 更值得写进案例。
6. **交付不是「能跑」，是「别人能独立用起来」。** 安装器、整库备份/恢复、关于与诊断、5 步上手引导；空库冷启动 5 分钟能走完「导入 → 生成 → 建链 → 备份」。
7. **6 天发了 40+ 个版本，每个都能装、能回滚、有 CHANGELOG。** v0.13.0 的「删除论文」正在同一套流程里继续跑——案例不是终点快照，是仍在运转的流水线。
8. **边界写得和功能一样清楚**：30 篇人工质量评估没做、12 个 Agent 工具的真实对话端到端没验收、概念图谱 UI 暂时隐藏。没做的部分单独列表，不混进「已完成」。

## 五、口径与免责

- 所有数字以 `v0.13.0` 为准；`v0.12.0` 与 `v0.13.0` 的差异在 `00` 台账标注。
- 用户规模为**单用户真实库**（4 篇）+ 合成 30 篇规模回归，不代表多用户生产数据。
- 文中「用户」指本项目真实使用者（研究者本人）与由其行为推导的画像；未做正式用户访谈的结论都标了「假设」。
- 视觉稿、截图、架构图在 `docs/assets/`；原始交付文档在 `docs/`。
