## 一、一页结论

1. **形态决定架构**：产品是 DSH 插件，所以只有两个运行端——宿主里的服务端（Node）与客户端（Web），没有独立服务器、没有数据库服务。
2. **库就是一个文件夹**：Markdown/JSON/JSONL 落盘，索引是缓存，坏了可重建；可读、可备份、可迁移。
3. **86 条路由 + 12 个工具**是全部对外能力；路由按资源分组，工具读优先、写操作必须 `confirm:true`。
4. **无 bundler 的构建**：`src/client` 11 个分片、`src/server` 10 个分片，按文件名拼成 `lib/client.js` / `lib/index.js`；换部署确定性，不用处理打包器的运行时差异。
5. **证据是一等数据结构**：q-id + 页码 + bbox；链节点只能引用库内证据，答案必须带库内 q-id。
6. **本地优先是架构约束**：只把必要文本发给模型；令牌不入备份、不入日志；恢复有路径校验、快照与回滚。
7. **复杂度花在「解析、定位、一致性」上**，不花在「框架」上——没有 ORM、没有向量库、没有消息队列。

## 二、架构总览

```text
┌────────────────────────── DSH 宿主 ──────────────────────────┐
│  Web 客户端（浏览器）                                          │
│  ├─ 工作台 / 论文库 / 写作 三块界面                            │
│  ├─ 组件：slots + primitives + 自绘（h()，非 JSX）             │
│  └─ 状态：模块内 state + 事件广播（litkb:data / litkb:guide）   │
│                          │ fetch /api/litkb/*                  │
│  ────────────────────────┼──────────────────────────────────  │
│  插件服务端（宿主进程内，Node）                                 │
│  ├─ 86 条 HTTP 路由（library/parse/card/chain/theme/...）       │
│  ├─ 12 个 lit_* Agent 工具（读优先，写需 confirm）              │
│  ├─ 任务：解析 / 卡片 / 翻译 / 精读 / 建链（内存队列 + 进度）    │
│  └─ 文件库：papers / cards / blocks / chains / themes / drafts  │
│                          │                                      │
│  ────────────────────────┼──────────────────────────────────  │
│  外部能力（可选）：模型（卡片/精读/建链）、PaddleOCR、Crossref    │
└──────────────────────────────────────────────────────────────┘
```

### 2.1 双端职责

| 端 | 负责 | 不负责 |
|---|---|---|
| 客户端 | 界面、交互、选区、状态、可视化 | 文件 IO、模型调用、解析 |
| 服务端 | 路由、文件库、解析、任务、模型、工具 | 界面渲染 |
| 宿主 | 窗口、设置、slots、主题令牌 | 业务逻辑 |

**边界**：客户端不直接读文件；服务端不假设界面存在。所有跨端交互走 HTTP。

### 2.2 为什么不是「独立 Web 应用」

- 用户已经在 DSH 里工作，插件能直接用侧边栏、主面板、设置、主题；
- 数据在本地，省掉账号、鉴权、部署、运维；
- 代价：受宿主 API 约束、客户端只能单文件加载（见 §7）。

## 三、数据与文件

### 3.1 库结构

```text
~/Documents/文献库/
├── papers/          原始 PDF
├── text/            分页文本、解析稿（派生，可删）
├── blocks/          版面块（page/bbox/text）
├── cards/           七段卡 JSON/MD + .versions/
├── translations/    译文（按块缓存）
├── deepread/        精读 11 板块
├── chains/          证据链（claim + nodes + relation）
├── themes/          研究（细分、覆盖、结论、文稿绑定）
├── drafts/          文稿
├── concepts/        受控概念、边、单篇缓存
├── exports/         导出产物
├── cache/           页图、检索历史、主题任务、备份快照
├── index.jsonl      论文索引（行式，读取时兼容旧字段）
├── tags.json / glossary.json / topics.json / settings.json
```

### 3.2 关键 schema

| 对象 | 字段（核心） |
|---|---|
| `Paper` | `id, citekey, title, authors, year, doi, tags, sha256, quality, status` |
| `Block` | `id, paperId, page, bbox, text, order, column` |
| `Evidence` | `id(q-xxxx), paperId, quote, page, blockId, kind` |
| `Chain` | `id, claim, nodes[], relation, status(draft/confirmed), basis` |
| `Theme` | `id, title, facets[], paperIds[], conclusions[], draftIds[]` |
| `Draft` | `id, title, body, citations[], updatedAt` |

### 3.3 存储决策

| 决策 | 选择 | 理由 |
|---|---|---|
| 主存储 | JSON/JSONL + Markdown | 可读、可 diff、可手工修、可备份 |
| 索引 | `index.jsonl` | 启动快、逐行修复、无数据库进程 |
| 派生数据 | `text/`、`cache/pages/` | 可删可重建，不进入备份 |
| 版本 | 卡片 `.versions/` | 单卡片回滚，不影响全局 |

## 四、接口

### 4.1 路由分组（86 条，v0.13.0）

| 组 | 典型路由 | 职责 |
|---|---|---|
| 健康/诊断 | `GET /health`、`GET /diag` | 版本、运行时、库计数、最近任务 |
| 论文库 | `GET/POST /papers`、`GET /paper`、`POST /update`、`POST /reclassify`、`GET/POST /delete` | 列表、详情、编辑、重分类、删除（影响面 + 二次确认） |
| 导入 | `POST /import`、`POST /import/link`、`GET/POST /ingest` | PDF、DOI/arXiv、自动管线 |
| 解析 | `POST /parse`、`GET /pdf`、`GET /page`、`GET /blocks` | 文本、页图、块 |
| 卡片 | `POST /card`、`POST /card/section`、`POST /card/evidence` | 生成、逐段、证据 |
| 精读 | `POST /deepread`、`POST /deepread/section` | 整篇/逐段 |
| 证据/链 | `POST /evidence`、`GET/POST /chains`、`POST /chains/dedupe`、`POST /chains/cross` | 建链、去重、跨论文 |
| 研究 | `GET/POST /themes`、`POST /themes/match`、`/themes/chain`、`/themes/jobs/*` | 细分、匹配、建链、任务 |
| 检索/问答 | `POST /search`、`POST /answer`、`GET/POST /search/history` | BM25、链优先答案 |
| 写作 | `GET/POST /drafts`、`POST /drafts/cite`、`POST /drafts/expand` | 文稿、引用、扩写 |
| 导出 | `/export/bibtex`、`/export/gbt`、`/export/card`、`/export/graph`、`/export/vault` | 多格式 |
| 数据 | `GET /backup`、`POST /restore`、`GET/POST /settings` | 备份、恢复、设置 |
| 上手 | `GET /onboarding` | 5 步进度（按真实库计算） |
| Agent | `lit_*` 12 个工具 | 读/写（写需 confirm） |

### 4.2 错误约定

- 错误码语义化：`confirm_required`(428)、`too_large`(413)、`bad_zip/bad_entry/bad_manifest`(422)、`restore_busy`(409)；
- 每个错误带可读文案与下一步（重试/换文件/重启）；
- 失败不返回 200 + `ok:false` 混用（除兼容旧客户端）。

## 五、Agent 工具

| 工具 | 读/写 | 作用 |
|---|---|---|
| `lit_search` | 读 | 检索证据/链 |
| `lit_card` | 读 | 七段卡 |
| `lit_blocks` | 读 | 解析块 |
| `lit_cite` | 读 | 取带页码引用 |
| `lit_graph` | 读 | 概念/链图 |

## 六、核心管线

### 6.1 解析 → 块 → 证据

```text
PDF → pdfjs 文本（/PaddleOCR 兜底）→ 页/块（bbox）
  → 段落重建（跨块、跨页续句；双栏先左后右）
  → 质量分 → 解析稿
  → 选区/批注 → q-id 证据（quote + page + blockId）
  → 页图渲染 → 点击块/证据 → 高亮
```

**难点**：中文双栏顺序、跨页段落、扫描件；处理原则是「宁可标失败，不许猜」。

### 6.2 链

```text
claim + nodes[]（q-id）+ relation
  → 草稿（自动/手动/主题）
  → 审核（确认/拒绝/编辑）
  → confirmed（进检索与图谱）
  → 合并去重（一细分一主链）
  → 失效检测（证据删除/块缺失）
```

### 6.3 检索与答案

```text
查询 → BM25（证据/链）→ 链优先组装
  → 有模型：生成答案 + 引用校验（只允许库内 q-id）
  → 无模型：抽取式摘要 + 页码
  → 过滤/复制/存为文稿/历史
```

### 6.4 备份与恢复

```text
备份：业务目录 → zip + manifest（排除 settings/cache）
恢复：校验 zip/manifest/路径 → staging → 当前库快照
      → 逐目录替换 → 失败回滚 → 清理
```

限制：包 ≤ 512MB、解压 ≤ 2GB、恢复中 409、错误码明确。

## 七、构建与分发

### 7.1 无 bundler 的拼接

```text
src/client/00-base.js … 70-apply.js  ──按文件名排序拼接──▶ lib/client.js
src/server/00-imports.js … 80-routes.js ──按文件名排序拼接──▶ lib/index.js
```

| 决策 | 理由 |
|---|---|
| 不用 bundler | 宿主按单文件加载；省掉打包器版本/插件/缓存问题 |
| 源码分片 | 按功能分区，单文件仍可读 |
| 生成物不手改 | `lib/` 头部有「不要直接编辑」提示；改 `src/` |
| 零运行时依赖（客户端） | 减少体积与兼容风险；图谱用宿主可用的 Cytoscape |

### 7.2 版本与产物

- `package.json` / `package-lock.json` / `dsh.plugin.json` 三处同步；
- `npm pack` → `dsh-litkb-<version>.tgz`；
- 安装器写 profile manifest、补 bundle、`pnpm install`，失败还原；
- 提示词在 `prompts/` 版本化（10 个），改 prompt 记 CHANGELOG。

## 八、安全与隐私

| 项 | 做法 |
|---|---|
| 数据位置 | 本机文件夹，默认 `~/Documents/文献库`，`LITKB_LIBRARY` 可覆盖 |
| 外发 | 只把必要文本发给模型/OCR；不上传整库、不上传 PDF |
| 令牌 | `settings.json` 不入备份、不入日志、不进提交 |
| 路径 | 恢复时拒绝绝对路径、`..`、空段；staging 解压 |
| 体积 | zip ≤ 512MB、解压 ≤ 2GB，防 zip bomb |
| 并发 | 恢复中再次请求 409 |
| 遥测 | 无 |

## 九、技术决策记录

| # | 决策 | 选择 | 放弃 | 理由 |
|---|---|---|---|---|
| D1 | 存储 | 文件 + JSONL | SQLite/服务端 DB | 可读、可备份、无进程 |
| D2 | 架构 | 双端插件 | 独立 Web 应用 | 复用宿主界面与设置 |
| D3 | 构建 | 字符串拼接 | Vite/esbuild | 宿主单文件加载，零构建依赖 |
| D4 | 检索 | BM25 | 向量库 | 百篇级够用，先不做复杂度 |
| D5 | 解析 | pdfjs 主 + OCR 兜底 | 只做 OCR | 速度与成本；扫描件再兜底 |
| D6 | 证据 | q-id + bbox | 纯文本引用 | 可跳转、可高亮、可校验 |
| D7 | 自动链 | 草稿 + 审核 | 直接入库 | 污染成本高于审核成本 |
| D8 | 测试 | 临时库 + 真实库干跑 | 只做 mock | 假数据测不出解析/页码问题 |

## 十、风险与边界

| 风险/边界 | 影响 | 处理 |
|---|---|---|
| 中文扫描件解析差 | 卡片/证据质量下降 | 质量分 + OCR 兜底 + 显式标记 |
| 跨页/双栏段落 | 证据定位偏移 | 段落重建 + 块高亮 + 人工可改 |
| 模型幻觉 | 引用错误 | 只允许库内 q-id；答案校验；无模型降级 |
| 宿主 API 变化 | 插件失效 | 版本约束 + 冒烟测试 + 安装器 |
| 无 bundler 的单文件膨胀 | 客户端 533KB | 分片源码 + 按功能加载；暂可接受 |
| 无类型检查 | 重构风险 | 测试 + 命名约定；类型检查列为 P3 |

---

## 十一、结论

技术方案的核心是**把复杂度放在数据与证据上，而不是框架上**：
文件库 + 双端插件 + 无 bundler + BM25 + q-id，五个选择都不「先进」，但每一个都让「装得上、搬得走、查得到」更确定。
