# 分工与验收协议（v1.0）

> 角色：**我负责开发与自测，你负责产品验收**——你只看"能不能用、好不好用、可不可信"，不看代码、不读需求文档、不测边界条件。
> 目的：让验收变成 5 个 15 分钟的演示，而不是一场考试。

---

## 1. 分工边界

| 事项 | 我（开发） | 你（产品验收） |
|---|---|---|
| 写代码、设计数据结构、选实现方案 | ✅ | — |
| 自测：单测、异常路径、性能 | ✅ | — |
| 装包、卸载、升级、冒烟 | ✅ | 只在 G1 / G5 做一次"冷启动"复核 |
| 判断"场景是否真的被解决" | — | ✅ |
| 判断"是否好用、要不要说明书" | 提供演示 | ✅ |
| 判断"结论可不可信" | 提供证据链 | ✅ 抽查 |
| 需求变更 | 提影响评估 | ✅ 拍板 |

**我不做的事**：不替你判断"这个功能值不值得做"、不把未完成说成完成、不拿测试数据冒充真实数据。
**你不做的事**：不 review 代码、不逐条核对 FR、不测断电/大文件/奇怪 PDF——那些是我的活。

---

## 2. 验收原则

1. **按场景验收，不按需求编号验收**——你不必知道 FR-704 是什么，只需要知道"点证据能不能跳过去"。
2. **只验结果，不验过程**——装完之后能用就行，怎么实现的与你无关。
3. **每项都可当场复现**——验收单上的每一条，你都能在 3 分钟内自己点一遍。
4. **不通过要给现象**——"哪个场景、你点了什么、看到什么、期望什么"，一句话即可。
5. **我不自证通过**——每次交付附"已知问题清单"，隐瞒问题比有问题更严重。

## 4. 验收流程

### 4.1 节奏

| 时点 | 我给什么 | 你要多久 |
|---|---|---|
| Day 0 | 前置确认清单 | 30 分钟（一起过一遍） |
| G1、G2 | 安装包 + 3 分钟演示脚本 + 验收单 | 各 15 分钟 |
| G3、G4 | 同上 + 指标数据 | 各 15 分钟 |
| G5 | 同上 + 已知问题清单 | 30 分钟 |

### 4.2 每次交付的"验收包"

1. **一条安装命令**（复制即用）；
2. **3 分钟演示脚本**（你照着点，不用想）；
3. **本阶段验收单**（勾选，见 §3）；
4. **已知问题清单**（诚实列出，含影响范围）；
5. **数据**：耗时、成本、准确率、覆盖率。

### 4.3 结论三态

| 结论 | 含义 | 后续 |
|---|---|---|
| ✅ 通过 | 4 条全过 | 进入下一阶段 |
| 🟡 有条件通过 | 主路径可用，遗留项不影响本阶段产品价值 | 记入遗留清单，下一阶段首日修 |
| ❌ 不通过 | 任一主路径不可用 | 我修，**复用本阶段缓冲**，最多返工两次 |

**两次不通过的规则**：停下来一起看是不是范围定错了，而不是硬修。

### 4.4 你的反馈格式（一句话即可）

```
场景：G3-2 点证据
现象：点了没反应，PDF 没跳
期望：跳到第 5 页并高亮
```

不需要写原因分析，也不需要提解决方案——那是我的事。

## 6. 争议与范围

| 情况 | 处理 |
|---|---|
| 你觉得"不好用"但说不出哪条 | 我请你在演示里走一遍，记录卡住的地方，转为具体问题 |
| 你要加功能 | 进 `待定清单`，v1.1 评估；不进当前阶段 |
| 我觉得某条需求不现实 | 我给出替代方案与代价，你拍板 |
| 验收通过后又发现重大问题 | 视同不通过，回到该阶段修，不追责 |

**唯一例外**：装不上、数据丢失、引用错误——这三类可以随时打断排期。
